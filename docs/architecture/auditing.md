# Auditing

Security administration and authentication write append-only records to `platform.audit_logs`. Role creation, role-permission replacement, and user-role replacement add their audit entry to the same `PlatformDbContext` transaction as the change, so neither side can commit independently. Successful sign-in, known-user sign-in failure, and logout are also recorded. A successful login is audited before its cookie is issued; logout clears its cookie even when audit persistence fails.

Every record carries tenant and optional company/user identifiers, UTC time, correlation and IP information, an action and entity identity, and optional JSONB metadata plus before/after snapshots. Producers record security and operational metadata and, where required, business-document snapshots; credentials, cookies, tokens, and authentication secrets must never be supplied. Actor identifiers are retained even if a user is later removed.

Tenant query filters isolate reads. `GET /api/v1/platform/audit` requires `platform.audit.read`, uses offset/limit pagination with a maximum page size of 100, and projects public contracts rather than persistence entities. The DbContext rejects updates and deletes for tracked audit records. Production database roles should additionally deny direct application `UPDATE` and `DELETE` access to `platform.audit_logs`. The [runtime provisioning script](../../eng/provision-postgres-runtime.sql) separates migration and runtime identities, but its general table DML grants do not enforce this additional audit-table restriction; review and apply that restriction after provisioning or reapplying grants.

Failed sign-in metadata contains only `invalid_credentials` or `locked_out`; submitted sign-in emails, passwords, cookies, and tokens are never persisted in authentication audit records. An unknown email cannot be associated with a trustworthy tenant and is therefore left to structured security logging and rate-limit telemetry rather than inserted into tenant audit history.

Module installation, update, enablement, and disablement already append audit records, as do business workflows such as contact changes and document transitions. New privileged operations must retain that coverage and document their transaction boundary. Contacts and Products mutations now enlist their business and platform audit contexts in one PostgreSQL transaction. Other modules still need explicit adoption; separate context saves are not automatically atomic. See the [Contacts audit consistency notes](../modules/contacts.md#audit-consistency), [Products audit consistency notes](../modules/products.md#audit-consistency), and [business transaction boundary](overview.md#business-transaction-boundary).
