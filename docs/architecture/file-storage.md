# File storage and attachments

`IFileStorage` is the blob boundary used by the platform and modules. It exposes streaming write/read, existence, and deletion operations so callers do not need to buffer whole files or know which provider is active.

Two providers are available:

- `LocalFileStorage` is the development default. It confines generated storage keys beneath one configured root, rejects rooted and traversal paths, and writes through a temporary file followed by an atomic move.
- `S3CompatibleFileStorage` uses the AWS S3 SDK and supports AWS S3 plus compatible services such as MinIO. A custom service URL, region, path-style access, bucket, and optional explicit credentials can be configured. When explicit credentials are omitted, the SDK credential chain is used.

Generic attachment metadata is persisted in `platform.attachments`; blob bytes are not stored in PostgreSQL. Storage keys are generated by the platform from tenant, company, and attachment identifiers and are never accepted from clients. Uploads enforce a configured byte limit and verify the declared length against the streamed content. If metadata persistence fails, the newly written blob is removed.

The API uses `platform.attachment.read` for listing/downloading and `platform.attachment.manage` for uploads. Uploads send the raw body, `Content-Type`, and an `X-File-Name` header to `POST /api/v1/platform/attachments?entityType=...&entityId=...`. Requiring a custom header also prevents a cross-site simple-request upload when cookie authentication is used.

`IFileMalwareScanner` is the provider-neutral scanning boundary. When a scanner is available, uploads are buffered to a bounded temporary file, scanned before storage, rewound, and then persisted. Set `FileStorage__RequireMalwareScanner=true` to fail closed when no scanner implementation is registered.

Local storage is persisted in the `erp-files` Docker volume. Production deployments should use durable object storage and its encryption, retention, backup, and lifecycle controls. Deployments accepting files from untrusted users should provide a scanner implementation and enable the fail-closed requirement. The local provider has filesystem contract coverage and the S3-compatible provider is exercised against real MinIO in the Docker-enabled integration suite. Orphan reconciliation remains future work.
